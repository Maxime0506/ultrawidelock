# `ai/`

Machine learning that runs on the lock, and the host-side work that decides what
goes there. Nothing in this tree is built or flashed by the firmware targets:
it is the bench that picked the runtime and the model that now ship in
[`modules/woz_ml/`](../modules/woz_ml/).

| directory | what | status |
|---|---|---|
| [`tinyml/`](tinyml/) | UWB line-of-sight / non-line-of-sight classification: framework bake-off, feature extractor, results | runtime chosen, model trained on this board, wired into the unlock path behind `make mlgate` |

## What this tree produced

[`modules/woz_ml/`](../modules/woz_ml/) is the product: a line-of-sight versus
obstructed classifier compiled into the lock firmware and, as of `c3294ad9`,
wired into the unlock decision. It answers a question the ranging distance
cannot: an obstructed 1 m and a clear 3 m produce similar time-of-flight
estimates and mean opposite things to a lock deciding whether the phone is
inside or outside a door.

On target the pipeline is four steps:

1. **Capture.** `uwb_cirdiag.c` latches five integer registers the DW3000
   already reports per reception: Ipatov F1/F2/F3, accumulator count and
   channel area.
2. **Features.** `woz_ml_los_features()` turns them plus the ranged distance
   into two floats, `fp_resid` and `rx_pwr`, with logarithms from a nine-entry
   table so the module links no libc.
3. **Classify.** `woz_ml_los_classify()` quantises to int16 and walks a depth-2
   decision tree: two integer comparisons, **0.8800 ± 0.0251** balanced
   accuracy on 544 walk-ups captured from this board.
4. **Decide.** `firmware/src/main.c` feeds the class to the approach
   controller, which widens the unlock radius while a majority-of-five window
   says obstructed. It does not edit the range: the obstruction offset's sign
   replicated across two bodies and its magnitude did not, so the wiring
   spends only the sign.

The whole module is **776 B of flash, 0 B of RAM and 28 B of stack**, and it is
off by default: only `make mlgate` builds the image that runs it in the unlock
path, and the standard image is byte-identical without it. Four of its six
source files are generated by [`tinyml/gen_model.py`](tinyml/gen_model.py)
behind five gates whose strongest claim is that the C in flash is the model
scikit-learn trained: it classifies identically on every held-out sample. The
rest of this README records how that runtime and model were chosen.

## The decision this tree has already made

**An emlearn decision tree, not TensorFlow Lite Micro.** On the public eWINE UWB
data set, restricted to the features a DW3110 can actually produce, a depth-4
tree scores 0.8625. Cross-compiled for the CDK's Cortex-M4F at `-Os` it is
**126 bytes of code, 112 bytes of scaling constants and zero RAM**. The best int8
TFLM MLP scores 0.8662 at 2,440 bytes of payload, and the best random forest
0.8684 at 30,802 bytes. Neither earns its size, and TFLM would additionally cost
its interpreter: roughly 2 KB of core before kernels, 4 KB of stack for
`AllocateTensors()`, and an arena.

**What ships is trained on this board, not on eWINE.** 544 walk-up receptions
captured from a DWM3001CDK against an iPhone, unobstructed and with the phone
shielded by the wearer's body, give a **depth-2 tree on two features** at
**0.8800 ± 0.0251** balanced accuracy in **466 bytes** of flash and no RAM: 0.9%
of the shipping image's free flash. `modules/woz_ml/` is generated from those
captures.

**One of the two features is not a raw register.** `fp_resid` is first-path power
with free-space spreading at the measured range removed, `fp_pwr + 20·log10(d)`.
An obstructed 1 m and a clear 3 m produce similar absolute power, which is this
classifier's founding problem and only a problem while the model cannot tell the
two apart. It is worth **+13.5 points** over four absolute features when a whole
capture is held out, at two fewer features. The logarithm is a nine-entry table
and a leading-bit exponent rather than `log10f`, so the module still links no
libc at all.

The margin that matters is not between model classes. Decawave APS006's
">6 dB implies non-line-of-sight" rule of thumb scores 0.6668 on the public set
and 0.7431 refit on this board's captures, so learning anything at all is worth
**20 points** there and **11 points** here. That gap, not the 0.6 points
separating a tree from a neural network, is the reason this tree exists.

[`tinyml/RESULTS.md`](tinyml/RESULTS.md) has the full tables, four findings that
changed the plan, and the caveats. [`tinyml/PLAN.md`](tinyml/PLAN.md) is the
research survey the bake-off was run to test, kept with its primary
recommendation marked as superseded rather than deleted.

## Running it

The data set and the virtualenv are both gitignored: about 1.8 GB, all of it
regenerable.

```sh
python3.12 -m venv ai/tinyml/.venv
ai/tinyml/.venv/bin/pip install -r ai/tinyml/requirements.txt
# fetch UWB-LOS-NLOS-Data-Set into ai/tinyml/data/, then:
ai/tinyml/.venv/bin/python ai/tinyml/extract_features.py
ai/tinyml/.venv/bin/python ai/tinyml/bakeoff.py
```

The on-target size measurement needs a cross compiler
(`brew install arm-none-eabi-gcc`) and the DW3000-portable feature set:

```sh
PORTABLE=1 WIN_PRE=32 WIN_POST=32 OUT=ai/tinyml/features_dw3000.npz \
    ai/tinyml/.venv/bin/python ai/tinyml/extract_features.py
ai/tinyml/.venv/bin/python ai/tinyml/codesize.py
```

`extract_features.py` takes `EWINE_DIR`, `OUT`, `WIN_PRE`, `WIN_POST` and
`PORTABLE`; `bakeoff.py` takes `FEATURES`, `OUTDIR`, `SEED` and `SUBSET`;
`codesize.py` takes `FEATURES`, `OUTDIR`, `SEED`, `CC` and `DEPTHS`. Each
script's docstring is the authority on what it does.

**Never run two bake-offs at once from the same working directory.** emlearn
compiles its Python-callable extension to a fixed path, `./tmp/mytree.{c,h,o}`,
regardless of the model name passed to `save()`, so concurrent runs overwrite
each other and one silently loads the other's binary. The failure looks exactly
like a model bug.

## Where this connects to the firmware

`modules/woz_uwb/src/driver/uwb_cirdiag.c` already captures what a model needs:
it latches `dwt_rxdiag_t` and reads 64 Ipatov channel-impulse-response taps
centred on the first-path index, emitting `[ALAB] ev=uwb.diag` and
`[ALAB] ev=uwb.cir` lines. The feature extractor's 64-tap window
(`WIN_PRE=32 WIN_POST=32`) exists to match that capture exactly.

`make cirdiag` builds the image that collects them on the DWM3001CDK, and
[`firmware/README.md`](../firmware/README.md) explains why it has to run the
capture cycle unattended: that board has no console input at all, so the
documented `aliro cir dump on` workflow is unavailable on it.

One difference to carry into any on-target extractor: the firmware emits complex
taps as `re=`/`im=` pairs, while the public data set ships magnitudes, so the
target has to compute `sqrt(re^2 + im^2)` before the shape features or training
and inference will not agree.
