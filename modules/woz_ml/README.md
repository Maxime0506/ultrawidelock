# `woz_ml`

On-device classifiers. One so far: line-of-sight versus obstructed, from the
DW3000's own receive diagnostics.

It answers a question the ranging distance cannot. An obstructed 1 m and a clear
3 m produce similar time-of-flight estimates and mean entirely different things
to a lock deciding whether the phone is inside or outside a door.

| | |
|---|---|
| Model | depth-2 decision tree, 2 integer comparisons |
| Accuracy | 0.8800 ± 0.0251 on 544 walk-ups captured from this board |
| Flash | 776 B: extractor, classifier, range correction and drift monitor together |
| RAM | 0 B. 28 B of stack |
| Kconfig | `CONFIG_WOZ_ML_LOS`, default n. No image enables it |
| Portability | plain C99, no libc, no float division. Builds anywhere |

## Why a tree and not a neural network

Measured, not assumed. Against the same features, the best int8 TensorFlow Lite
Micro network scored 0.8662 for 2,440 B of payload before its interpreter, and
the best random forest 0.8684 for 30,802 B. The 0.4 accuracy points between a
tree and a network do not pay for roughly 2 KB of interpreter core, 4 KB of
`AllocateTensors()` stack and an arena, on a part with 20 KB of RAM left.

The margin that justifies doing this at all is elsewhere. Decawave APS006's
">6 dB implies non-line-of-sight" rule of thumb scores 0.667 on the public set
and 0.7431 refit on this board's own captures, so learning anything is worth
**20 points** there and **11 points** here. That gap is the point; the choice of
model class is a rounding error beside it.

Full tables, and the four findings that changed the plan, are in
[`ai/tinyml/RESULTS.md`](../../ai/tinyml/RESULTS.md).

## What is generated, and what certifies it

Four of the six source files are generated by
[`ai/tinyml/gen_model.py`](../../ai/tinyml/gen_model.py) and must never be
hand-edited:

| file | what |
|---|---|
| `include/woz_ml_los_features.h` | feature count and order: the public contract |
| `src/woz_ml_los_scaler.h` | the float32 scaling constants, `static const`, one TU only |
| `src/woz_ml_los_tree.h` | emlearn `inline` C for the tree |
| `src/woz_ml_log2_table.h` | nine entries of `log2(1+x)`, so nothing here needs libm |

Regenerate with:

```sh
ai/tinyml/.venv/bin/python ai/tinyml/gen_model.py
```

Bare, with no environment variables: every default in the generator is the
shipped model, and a bare run reproduces these four files byte for byte. It did
not always, and the failure was silent -- the defaults described the public
eWINE set at depth 4 while the shipped model was 544 door captures at depth 2,
so following this instruction replaced the shipped tree with a different model
while every gate below reported zero. The gates certify the C against whatever
was just fitted, not against what ships, so they cannot catch that. The defaults
being right is what catches it.

The generator refuses to write anything unless five gates pass:

0. **Pruning changed no prediction.** scikit-learn fits splits that separate
   samples without changing the answer, because they still lower impurity: the
   fitted tree has 7 nodes and 4 leaves, of which only 5 nodes and 3 leaves
   decide anything. The generator collapses the rest and verifies the result
   predicts identically on all 544 samples. This buys no flash -- the compiler
   was already folding those branches -- but it makes the generated C say what
   the model actually decides, and it is what clang-tidy's
   `bugprone-branch-clone` was correctly complaining about.
1. **The generated C reproduces scikit-learn** on all 82 held-out samples.
   This is possible only because the model is a single tree. A random forest's
   generated C disagrees with scikit-learn on 0.92% of samples at emlearn's
   default settings. That default is `leaf_bits=0`, majority voting;
   `leaf_bits=8` selects soft voting and brings it to 0.06%. Still not zero, so
   a forest still cannot be held to this gate — but it misses by 4 samples in
   6,300 rather than 58, and anyone revisiting it should start there rather than
   from the older claim that scikit-learn has to be demoted to advisory. Measured
   in RESULTS.md Result 14.
2. **The float32 scaler agrees with the float64 one** the model was trained
   through, on every held-out sample. At the last regeneration 6 of 336
   quantised values landed one LSB apart and none of them changed a class. That
   margin is the whole reason the gate exists, and `quantise_f32()` in the
   generator simulates the exact expression `quantise()` in `src/woz_ml_los.c`
   computes, down to the rounding mode. Change one without the other and the
   gate goes quietly hollow.
3. **The table-based range correction classifies identically to `numpy.log10`.**
   `fp_resid` is trained through float64 logarithms and computed on target from a
   leading-bit exponent and eight table entries. Those are different functions, so
   the generator recomputes every sample's residual the way the target will and
   refuses to write unless the class is unchanged: currently 0 of 544, with a
   maximum error of 0.183 dB. That error is dominated by range arriving as a whole
   number of centimetres, not by the table, which is why the table is only eight
   entries. See `src/woz_ml_range.c`.
4. **The on-target feature extractor classifies identically to float64.** Gates
   1-3 all begin from features the generator computed in float64. Nothing checked
   the path that begins at the registers the radio reports and runs through a
   64-bit sum of squares, a `2^17` channel-area scaling and three interpolated
   logarithms. `src/woz_ml_feat.c` is that path, and this is its gate: 0 of 544
   classifications changed, 0.0099 dB maximum error on the powers.

   The raw capture logs are not tracked, so the registers are recovered by
   inverting the formulas that produced the tracked CSV. That is only legitimate
   if the inversion is lossless, so the gate checks that first and separately and
   aborts if it is not: currently the recovered integers reproduce the recorded
   decibels to 4.4e-10 dB. Without that check the gate could compare the C
   against numbers the hardware never produced and still report zero.

`tests/host/test_woz_ml.c` carries gate 1's claim into CI with 82 vectors
stratified over the pruned tree's 3 leaves, so every decision path is exercised,
and the expected answers are scikit-learn's own.

These gates were sized for the public set's 42,000 samples and now run on 544.
The claim they certify is unchanged -- the C is the model that was trained --
but 82 held-out samples is a narrower proof than 6,300, and the honest reading
is that they catch a broken generator, not a subtly wrong one.

## What this is not

**Nothing calls it.** It is compiled, certified and sized; it is not wired to a
decision. Wiring it has to answer what a wrong answer costs at a door, and that
is a separate change.

**The features are produced on target now, but nothing reads the radio.**
`woz_ml_los_features()` takes the five Ipatov CIA registers and the ranging
distance and fills the vector, reproducing `ai/tinyml/parse_alab.py` register
for register under gate 4. What is still unwritten is the caller: something that
reads a `dwt_rxdiag_t` out of the driver, copies five fields into a
`struct woz_ml_cia`, and does something with the answer.
`modules/woz_uwb/src/driver/uwb_cirdiag.c` already reads exactly that struct and
emits it as `[ALAB] ev=uwb.diag`, so the material is there; deciding when to
classify, and what a class is worth, is the change that has not been made.

**One room, one phone, one person, one day.** The 544 captures came from a single
morning and afternoon against one iPhone in one space. Both sides do survive
holding out a whole capture (RESULTS.md Result 9), but the two unobstructed
sessions still differ by 2.9 dB in mean `fp_pwr`, about a third of the
obstruction signal, which is what the range correction exists to remove. At 776 B
the model is cheaper to retrain at an install than to transfer to one.

**Absolute power carries it.** A single threshold on `fp_pwr` alone scores
0.8207 against the tree's 0.8800, so most of what the model knows is "the signal
got weaker, by more than the range explains". That is genuinely what a body does to 6.5 GHz, but it also means
anything else that attenuates -- a different phone, a pocket, a coat -- moves the
thresholds. `rxpacc` contributes almost nothing: 0.5597 alone, against 0.5000
for a coin flip.
